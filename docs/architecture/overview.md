# 아키텍처 개요

제품 요구사항과 논리 ERD는 저장소에 보관하며 외부 문서 서비스 연결 없이 설계와 구현을 진행한다. 데이터 구조는 docs/architecture/erd.md를 기준으로 한다.

## 1차 로컬 구성

- FastAPI API 프로세스
- PostgreSQL 개발 데이터베이스
- PostgreSQL 테스트 데이터베이스
- 이메일 인증과 리마인더를 확인할 로컬 SMTP 수신함
- 리마인더 스케줄러 또는 작업자 프로세스
- 결정적으로 적재되는 제품, 의약품과 영양소 기준 데이터

애플리케이션 런타임은 Python 3.12, FastAPI, SQLAlchemy 2 동기 세션, psycopg 3와
Alembic을 사용한다. Python 의존성은 uv.lock으로 고정한다.

Docker Compose는 실행 편의를 제공하지만 애플리케이션 코드는 Compose 자체에 의존하지 않는다.

## 계층 의존 방향

API 계층 → 애플리케이션 서비스 → 도메인 모델 → 저장소와 외부 포트

인증, 카탈로그, 마이케어와 알림 도메인은 서로의 DB 테이블을 직접 조작하지 않는다. 필요한 데이터는 공개된 애플리케이션 서비스 또는 저장소 계약을 통해 사용한다.

## 교체 가능한 경계

- 시계: 운영 시계와 가짜 시계
- 이메일 발신기: 로컬 SMTP, 가짜 발신기와 2차 운영 공급자
- 스케줄러: 로컬 작업자와 2차 관리형 스케줄러
- 객체 저장소: 로컬 또는 시드 URL과 2차 객체 저장소
- 코칭 소비자: 안정된 조회 계약을 사용하는 2차 모듈

## 실행 원칙

- API는 가능한 한 무상태로 유지한다.
- DB 시간은 UTC로 저장하고 사용자 표시와 예약 경계에서 서비스 시간대를 적용한다.
- 외부 호출 실패가 DB 트랜잭션을 장시간 점유하지 않게 한다.
- 알림 생성과 발송은 분리하고 각각 멱등성을 보장한다.
- API와 작업자는 같은 애플리케이션 이미지를 사용하지만 별도 프로세스로 실행한다.
