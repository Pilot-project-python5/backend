# 저장소 요구사항 기준

이 문서는 알약꾹 백엔드의 기능 명세·구현·검증에 사용하는 로컬 요구사항 원본이다. 외부 문서 서비스에 접속하지 않고도 작업할 수 있도록 확정된 제품 정책을 보관한다.

## 문서 권위와 변경 규칙

- 이 문서와 승인된 Feature Packet을 구현 권위로 사용한다.
- 기능 ID, 단계, 담당과 상태는 docs/features/manifest.yaml에서 관리한다.
- 기능 하나의 상세 API·데이터·인수 조건은 해당 Feature Packet에서 확정한다.
- 사용자 결정이 바뀌면 코드보다 이 문서와 관련 Feature Packet을 먼저 갱신한다.
- 외부 링크는 docs/source-map.md에 출처 이력으로만 보관한다.

## FR-1 회원과 인증

### 회원가입

- 이름, 로그인 아이디, 비밀번호, 비밀번호 확인, 이메일, 생년월일, 성별, 키와 몸무게를 입력한다.
- 숫자 나이는 저장하지 않고 생년월일과 계산 기준일로 계산한다.
- 로그인 아이디는 정규화 후 고유하게 관리한다.
- 비밀번호 원문을 저장하거나 로그에 남기지 않는다.
- 이메일 인증 전에는 로그인을 허용하지 않는다.

### 이메일 인증

- 6자리 인증번호를 이메일로 전송한다.
- 인증번호 유효시간은 10분이다.
- 재전송 대기시간은 60초다.
- 최대 5회 실패 제한을 적용한다.
- 인증번호 원문 대신 검증 가능한 해시를 저장한다.
- 1차에서는 로컬 SMTP 수신함과 가짜 이메일 발신기로 검증한다.

### 로그인과 세션

- 아이디와 비밀번호로 로그인한다.
- 인증 실패는 아이디 또는 비밀번호 중 어떤 값이 틀렸는지 노출하지 않는다.
- 액세스·리프레시 토큰은 HttpOnly 쿠키로 전달한다.
- 액세스 토큰 수명은 15분, 리프레시 토큰 수명은 14일이다.
- 쿠키는 SameSite=Lax를 사용하고 로컬에서는 Secure=false, 배포 환경에서는
  Secure=true로 설정한다.
- 로그인 성공마다 리프레시 세션을 새로 만들어 기기별 다중 로그인을 허용하고,
  리프레시 토큰 원문 대신 해시만 저장한다.
- 인증 갱신마다 리프레시 토큰을 회전하고 이전 토큰 재사용 시 해당 세션을 폐기한다.
- 리프레시 세션 만료는 최초 로그인부터 14일로 고정하며 갱신으로 연장하지 않는다.
- 로그아웃은 현재 리프레시 세션만 폐기하고 반복 호출할 수 있다.
- access JWT와 서버 리프레시 세션을 함께 검증해 로그아웃·세션 만료·계정 정지를
  보호 API에 즉시 반영한다.
- 현재 사용자 기본·건강 프로필과 access·refresh 만료 시각을 조회하고, access 만료
  뒤에는 명시적인 인증 갱신 또는 로그인 흐름을 제공한다.

## FR-2 전문가 큐레이션

- 전체, 비타민, 단백질, 오메가3 등의 활성 제품 카테고리를 제공한다.
- `전체`는 DB 카테고리가 아니라 필터 미적용을 뜻하는 가상 `all` 항목이며 항상
  첫 번째다. 실제 활성 카테고리는 sort_order와 slug로 안정적으로 정렬한다.
- 게시 상태인 추천 제품만 목록에 노출한다.
- 추천 제품 목록은 비회원 공개 API이며 category를 생략하거나 `all`로 보내면 전체,
  활성 category slug를 보내면 해당 분류만 조회한다. 알 수 없거나 비활성인 유효 slug는
  404로 구분한다.
- 목록은 편집 sort_order와 sku로 안정적으로 정렬하고 1부터 시작하는 page와
  1~100 범위 page_size, total과 has_next를 제공한다.
- 제품 이미지 URL, 카테고리, 브랜드, 제품명, 표시 가격, 구성 성분과 총 용량을 제공한다.
- 목록 카드 미리보기와 단일 제품의 패키지·성분 상세를 분리하며, 전문가 코멘트와
  외부 구매 연결은 각각 F-2.4.1과 F-2.4.2에서 독립적으로 확장한다.
- 단일 상세는 제품 UUID로 공개 조회하며 목록 공통 필드, 패키지 형태·총 단위 수와
  활성 구성 성분·단위당 함량을 제공한다. 공개 조건을 만족하지 않는 제품은 404로
  통일하고 성분이 없으면 빈 배열을 제공한다.
- 패키지 수량과 단위당 함량은 Decimal 정밀도를 보존하는 JSON 문자열로 제공하며
  1차 성분 단위는 MG, G, MCG, IU를 사용한다.
- 제품별 전문가 코멘트와 추천 이유를 제공한다.
- 활성 외부 구매 링크로 이동할 수 있게 한다.
- 서비스 내부 구매, 결제, 주문과 배송은 제공하지 않는다.
- 제품, 의약품, 성분, 코멘트와 구매 링크는 DB 시드로 관리한다.
- 전문가 소개는 1차에서 프론트엔드 정적 콘텐츠로 관리한다.
- 추천 소식 알림 F-2.5는 2차로 연기한다.

## FR-3 마이케어

### 복용 제품 등록

- 로그인 회원만 사용할 수 있다.
- DB 카탈로그에 존재하는 영양제와 의약품만 등록할 수 있다.
- 구매일과 별도 복용 시작일을 저장한다.
- 총 보유 수량, 회당 복용량과 하루 복용 횟수를 저장한다.
- 카탈로그에 없는 제품을 사용자가 직접 입력하지 않는다.
- 재등록은 기존 소진 기록을 덮어쓰지 않고 새 복용 항목으로 보존한다.

### 성분과 예정 섭취량

- 영양제 등록 시 제품의 구성 성분과 단위당 함량을 복용 항목의 스냅샷으로 보존한다.
- 카탈로그가 바뀌어도 기존 복용 항목의 계산 결과가 달라지지 않아야 한다.
- 일일 예정 섭취량은 단위당 함량 × 회당 복용량 × 하루 복용 횟수로 계산한다.
- 동일 성분은 변환 가능한 기준 단위로 맞춰 합산한다.
- 실제 복용 기록은 1차 범위에 포함하지 않는다.
- 의약품은 복용 목록, 재고와 유통기한 관리에는 포함하지만 영양소 합계에서는 제외한다.

### 영양소 기준 데이터

- 계산 시점의 나이와 성별에 맞는 기준량을 사용한다.
- 원본은 애플리케이션 코드와 분리된 CSV로 관리한다.
- 적재 전에 필수 열, 단위, 중복 키와 겹치는 나이 구간을 검증한다.
- 출처와 버전을 추적할 수 있어야 한다.

### 예상 소진일과 재고 상태

- 복용 시작일, 총 보유 수량, 회당 복용량과 하루 복용 횟수로 마지막 복용 예정일을 계산한다.
- 마지막 복용 예정일을 D-day로 사용한다.
- 소진 D-5부터 LOW_STOCK 상태다.
- D-day 다음 날부터 DEPLETED 상태다.
- 새 복용 항목 등록은 기존 소진 이력을 덮어쓰지 않는다.

### 유통기한

- 재고 상태와 유통기한 상태를 분리한다.
- 유통기한 상태는 NORMAL, EXPIRING_SOON, EXPIRED를 사용한다.
- 수량이 남아 있어도 유통기한이 지나면 EXPIRED가 될 수 있다.

### 화면 알림과 이메일

- 재구매와 유통기한 알림을 화면 내부와 이메일로 모두 제공한다.
- 알림은 D-5, D-3, D-1의 오전 9시에만 생성한다.
- 대상 복용 항목, 알림 종류, 기준일, 트리거 날짜와 채널 기준으로 중복을 방지한다.
- 작업자를 같은 날짜에 다시 실행해도 중복 생성하거나 발송하지 않는다.
- 화면 알림의 읽음 상태와 이메일 발송·재시도 상태를 보존한다.

## FR-4 AI 코칭

- AI 코칭 전체는 1차 MVP 범위에서 제외한다.
- 2차에서 다른 개발자가 안정된 조회 계약을 통해 연결한다.
- AI 모듈은 auth, catalog와 care 테이블을 직접 수정하지 않는다.
- 의료 진단과 처방을 생성하지 않으며 필요한 최소 건강정보만 사용한다.

## 1차 로컬 실행 요구사항

- FastAPI와 PostgreSQL 개발·테스트 DB를 사용한다.
- SQLite로 대체하지 않는다.
- 로컬 이메일 수신함과 로컬 알림 작업자를 사용한다.
- 마이그레이션은 빈 DB에서 재현 가능해야 한다.
- 시드는 반복 적재 가능하고 실제 개인정보·건강정보를 포함하지 않아야 한다.
- Swagger와 생성된 OpenAPI가 실제 요청·응답과 일치해야 한다.
- 단위, 통합, 계약과 인수 테스트를 제공한다.
- AWS 계정, 운영 이메일 공급자와 외부 AI 없이 전체 검증이 가능해야 한다.

## 1차 제외 범위

- AWS 또는 운영 서버 배포
- 운영 이메일 공급자
- 추천 소식 알림
- AI 코칭과 외부 LLM
- 의약품·영양제 상호작용 분석
- 실제 복용 여부 기록
- 카탈로그에 없는 제품 직접 입력
- 운영자 화면
- 서비스 내부 결제, 주문과 배송

## 확정이 필요한 정책

- 이메일 주소의 고유성
- 유통기한 입력의 필수 여부
- 복용 계획과 수량 수정 API 제공 여부
- 동일 제품의 미소진 재고가 있을 때 재구매 처리
- 복용 항목 삭제와 이력 보존 기간
- 나누어떨어지지 않는 수량의 마지막 복용일 계산
- 영양소 CSV 출처, 열, 단위, 변환과 버전 규칙
- 오전 9시의 IANA 기준 시간대
- 이메일 재시도 정책과 2차 운영 공급자
- 의약품 시드의 필수 필드와 분류 체계
