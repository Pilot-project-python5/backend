# F-3.8 재구매 상태·알림

## 목표

사용자가 예상 소진일까지 남은 날짜와 함께 정상·재구매 필요·소진 상태를 확인하고,
로컬 작업자가 정확한 D-5·D-3·D-1 오전 9시에 재구매 논리 알림을 한 번만 만들게 한다.

## 사용자 이야기

사용자로서, 복용 제품이 떨어지기 전에 다시 준비하기 위해 재고 상태를 보고 정해진
날짜에 중복 없는 재구매 알림을 받고 싶다.

## 비즈니스 규칙

1. inventory_status는 저장하지 않고 days_until_depletion으로 계산한다. D-6 이상은
   NORMAL, D-5부터 D0은 LOW_STOCK, 다음 날부터는 DEPLETED다.
2. 재구매 알림의 기준일은 CareItem.expected_depletion_date 하나이며 실제 잔량을
   추론하거나 새 구매분을 기존 항목과 합치지 않는다.
3. 활성 CareItem 중 KST 기준 D-5·D-3·D-1인 항목만 그날 오전 9시 이후 작업자 실행에서
   REPURCHASE 논리 알림을 만든다. 오전 9시 전과 D-4·D-2·D0·지난 날에는 만들지 않는다.
4. 작업자가 오전 9시 이후 늦게 시작해도 같은 로컬 날짜 안에는 알림을 만들지만,
   다음 날 누락 알림을 소급 생성하지 않는다.
5. 같은 구매분·종류·기준일·트리거 일수 조합은 작업자 재실행·동시 실행에도 한 건이다.
6. 알림 scheduled_at은 해당 로컬 날짜 오전 9시를 UTC로 변환한 값이고 created_at은
   실제 생성 시각이다.
7. 삭제된 CareItem은 상태 목록과 새 알림 대상에서 제외한다. 기존 논리 알림은 이후
   소프트 삭제로 지우지 않는다.
8. Notification은 화면과 이메일이 공유하는 논리 이벤트다. 이번 기능은 REPURCHASE
   생성까지만 담당하고 조회·읽음과 이메일 전달은 후속 기능이 담당한다.

## 포함 범위

- 활성 목록의 inventory_status
- D-5·D-3·D-1 오전 9시 이후 REPURCHASE 논리 알림 생성
- notifications ORM·마이그레이션·고유 제약·조회 인덱스
- 로컬 worker의 세션 단위 작업 실행과 중복 방지
- KST 경계·삭제 제외·장애·재실행 단위·통합·계약·인수 테스트

## 제외 범위

- F-3.9 화면 알림 목록·읽음 처리와 EXPIRATION 논리 알림 생성
- F-3.12 이메일 전달 행·SMTP 발송·재시도
- 실제 복용·잔량 보정, 소진 상태 수동 변경과 새 구매분 자동 연결
- 누락 날짜 소급 생성, 푸시·SMS, AWS 스케줄러와 운영 모니터링

## 시나리오

### 기본 흐름

- 사용자는 D-6에 NORMAL, D-5부터 D0에 LOW_STOCK, 다음 날 DEPLETED를 목록에서 본다.
- 작업자는 D-5·D-3·D-1 오전 9시 이후 실행될 때 해당 재구매 알림을 만들고 같은 날
  반복 실행에서는 0건을 추가한다.

### 실패와 경계

- 오전 8:59:59에는 생성하지 않고 9:00:00에는 생성한다.
- 삭제 항목, D-4·D-2·D0과 이미 지난 트리거는 생성하지 않는다.
- DB 장애는 작업 실행을 실패시키되 worker 루프가 다음 주기에 다시 시도한다.

## 미결 질문

- 없음. 오전 9시는 기존 APP_TIMEZONE(기본 Asia/Seoul)으로 확정했다. “화면 알림과
  이메일 생성”은 채널별 발송을 이번 기능에 섞지 않고 공유 Notification 논리 이벤트
  생성으로 해석했다. F-3.9가 화면 조회·읽음과 만료 이벤트를, F-3.12가 이메일 전달을
  담당해 중복 책임을 피한다.
