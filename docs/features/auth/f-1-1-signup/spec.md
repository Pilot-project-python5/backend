# F-1.1 회원가입

## 목표

웹 사용자가 로그인 아이디, 비밀번호, 이메일과 건강 프로필을 제출해 이메일 미인증
상태의 알약꾹 계정을 안전하게 생성할 수 있게 한다. 생성된 생년월일과 성별은 이후
나이·성별별 영양소 기준량 계산의 원본이 된다.

## 사용자 이야기

새 사용자로서, 이메일 인증을 진행할 계정과 건강 프로필을 만들기 위해 필수 가입
정보를 한 번에 등록하고 싶다.

## 비즈니스 규칙

1. 이름, 로그인 아이디, 비밀번호, 비밀번호 확인, 이메일, 생년월일, 성별, 키와
   몸무게를 모두 입력한다.
2. 로그인 아이디는 영문자와 숫자 5~20자로 받고 소문자로 정규화한 값을 고유하게
   관리한다.
3. 비밀번호는 8~20자이며 영문자, 숫자와 허용 특수문자를 각각 하나 이상 포함하고
   비밀번호 확인과 일치해야 한다.
4. 비밀번호 원문과 비밀번호 확인은 저장하거나 응답·로그에 남기지 않고 Argon2id로
   해시한 값만 저장한다.
5. 이메일은 앞뒤 공백을 제거하고 전체를 소문자로 정규화한다. 정규화 이메일은
   계정 전체에서 고유하다.
6. 이름은 앞뒤 공백을 제거한 1~50자 유니코드 문자열로 받는다.
7. 생년월일은 미래일 수 없으며 숫자 나이는 저장하지 않는다.
8. 성별은 1차 화면 범위인 MALE 또는 FEMALE로 제한한다.
9. 키는 50~250cm, 몸무게는 10~500kg 범위의 양수로 받는다.
10. 사용자와 건강 프로필은 하나의 트랜잭션에서 생성되며 어느 한쪽이 실패하면
    모두 저장하지 않는다.
11. 생성 직후 계정 상태는 PENDING_EMAIL_VERIFICATION이고 email_verified_at은
    null이다.
12. 동일한 정규화 로그인 아이디의 동시 요청은 DB 고유 제약으로 하나만 성공한다.
13. 성공 응답은 생성된 식별자와 인증 필요 상태만 반환하며 비밀번호 해시는 반환하지
    않는다.

## 포함 범위

- POST /api/v1/auth/signup
- 사용자와 건강 프로필의 원자적 생성
- 로그인 아이디 정규화와 중복 방지
- 이메일 정규화와 중복 방지
- 비밀번호 확인과 안전한 해시 저장
- 회원가입 요청·응답·오류의 Swagger/OpenAPI 계약
- users와 health_profiles 마이그레이션 및 ERD 일치

## 제외 범위

- 아이디 중복 확인 전용 API(F-1.1.1)
- 별도 가입 정보 검증 API(F-1.1.2)
- 인증번호 생성·발송·재전송·확인(F-1.1.3)
- 로그인과 인증 쿠키(F-1.2)
- 프로필 조회·수정·탈퇴
- 소셜 로그인, 약관 동의와 운영 이메일 공급자

## 시나리오

### 기본 흐름

1. 사용자가 모든 필수 가입 정보를 제출한다.
2. 서버가 입력을 검증하고 로그인 아이디와 이메일을 정규화한다.
3. 서버가 비밀번호를 해시하고 사용자와 건강 프로필을 한 트랜잭션으로 저장한다.
4. 서버가 201과 함께 사용자 식별자, 로그인 아이디, 이메일,
   PENDING_EMAIL_VERIFICATION 상태와 email_verification_required=true를 반환한다.

### 실패와 경계

- 필수값, 형식, 범위 또는 비밀번호 확인이 잘못되면 422 VALIDATION_FAILED를
  필드 단위 오류와 함께 반환한다.
- 정규화 로그인 아이디가 이미 존재하면 409 AUTH_LOGIN_ID_UNAVAILABLE을 반환한다.
- 중복 이메일은 409 AUTH_EMAIL_UNAVAILABLE을 반환한다.
- 경쟁 요청에서 고유 제약이 충돌해도 내부 DB 오류를 노출하지 않고 같은 409 계약을
  반환한다.
- 건강 프로필 저장이 실패하면 사용자 행도 남기지 않는다.
- 같은 요청의 재전송은 별도 멱등 키가 없으므로 기존 계정과 충돌한다.
