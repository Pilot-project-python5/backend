# F-1.1.2 가입 정보 검증

## 목표

사용자가 계정을 만들기 전에 전체 가입 정보의 형식과 의미, 로그인 아이디·이메일
중복을 한 번에 확인해 입력 오류를 미리 수정할 수 있게 한다.

## 사용자 이야기

신규 사용자로서, DB에 계정이나 건강 프로필을 만들지 않고 제출할 가입 정보가
유효한지 사전 확인하고 싶다.

## 비즈니스 규칙

1. F-1.1 회원가입과 동일한 SignupRequest 전체 필드와 검증 규칙을 재사용한다.
2. 필수값·문자 형식·범위·비밀번호 확인이 잘못되면 422 VALIDATION_FAILED를
   필드 단위로 반환한다.
3. 미래 생년월일과 정규화 로그인 아이디·이메일 중복은 200 응답의 issues로 함께
   반환하며 하나라도 있으면 valid=false다.
4. issue 순서는 login_id, email, birth_date 순으로 결정적으로 유지한다.
5. 로그인 아이디와 이메일은 F-1.1과 같은 소문자 정규화 규칙으로 조회한다.
6. 사전 검증은 비밀번호를 해시하거나 users·health_profiles를 생성·수정하지 않는다.
7. 검증 성공은 아이디나 이메일을 예약하지 않으며 실제 가입의 UNIQUE 제약이 최종
   중복을 판정한다.
8. PostgreSQL 조회 실패는 503 SERVICE_UNAVAILABLE로 변환한다.

## 포함 범위

- POST /api/v1/auth/signup/validation 공개 API
- 전체 가입 요청의 형식·필수값·범위·비밀번호 확인 검증
- 미래 생년월일과 로그인 아이디·이메일 중복의 일괄 결과
- 저장 없는 읽기 전용 사전 검증
- 요청·응답·오류 예시를 포함한 Swagger/OpenAPI 계약

## 제외 범위

- 사용자·건강 프로필 생성과 비밀번호 해시
- 아이디·이메일 예약 또는 선점
- 인증번호 생성·발송·확인
- 로그인, 세션, 속도 제한과 봇 방지
- 테이블·인덱스·마이그레이션·ERD·시드 변경

## 시나리오

### 기본 흐름

- 모든 값이 유효하고 중복이 없으면 200, valid=true, issues=[]를 반환한다.
- 아이디와 이메일이 모두 중복이면 200, valid=false와 두 field issue를 반환한다.
- 미래 생년월일과 중복이 함께 있으면 한 응답에서 모든 issue를 반환한다.

### 실패와 경계

- 필수값 누락, 잘못된 형식·범위 또는 비밀번호 불일치는 422다.
- 같은 DB 상태에서 같은 요청을 반복해도 데이터를 변경하지 않고 같은 결과를 반환한다.
- 검증 직후 다른 사용자가 먼저 가입할 수 있으므로 실제 가입의 409도 처리해야 한다.
- DB 조회 실패는 내부 SQL과 사용자 정보를 숨긴 503이다.

## 미결 질문

- 없음. 2026-08-11에 사용자가 전체 요청의 형식 검증과 아이디·이메일 중복을 저장 없이
  확인하는 계약을 승인했다.
