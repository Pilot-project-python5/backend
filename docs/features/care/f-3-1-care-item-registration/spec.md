# F-3.1 복용 제품 등록

## 목표

인증된 사용자가 서비스 DB 카탈로그의 영양제 또는 의약품을 구매일·복용 계획과
함께 마이케어에 등록한다. 같은 제품의 재구매도 과거 이력을 덮어쓰지 않고 별도
복용 항목으로 보존한다.

## 사용자 이야기

사용자로서, 내가 복용하는 카탈로그 제품의 수량과 복용 계획을 관리하기 위해
새 복용 항목으로 등록하고 싶다.

## 비즈니스 규칙

1. `POST /api/v1/care/items`는 유효한 access JWT 쿠키가 있는 사용자만 호출한다.
2. `product_id`는 DB 제품 카탈로그에 존재해야 하며 제품 유형은 영양제 또는
   의약품이다. 게시 여부는 등록 가능 여부에 영향을 주지 않는다.
3. 구매일은 서버 기준 오늘 이후일 수 없다.
4. 복용 시작일은 구매일보다 빠를 수 없고 미래 날짜일 수 있다.
5. 총수량과 1회 복용량은 0보다 크고 최대 `999999999.999`, 소수점 셋째 자리까지다.
6. 1회 복용량은 총수량을 초과할 수 없다.
7. 일일 복용 횟수는 1 이상 24 이하다.
8. 성공하면 새 복용 항목을 생성하고 201로 등록 값을 반환한다.
9. 같은 사용자가 같은 제품과 같은 날짜를 다시 등록해도 별도 행을 생성한다.
10. DB 장애는 내부 정보를 감춘 503 `SERVICE_UNAVAILABLE`로 변환한다.

## 포함 범위

- 인증·사용자 소유권이 적용된 복용 제품 등록 API
- care_items ORM·마이그레이션·ERD
- 카탈로그 제품 존재 확인
- 날짜·수량·일일 횟수 검증
- 단위·통합·계약·인수 테스트와 Swagger·OpenAPI

## 제외 범위

- 사용자 직접 제품 입력과 카탈로그 관리 API
- 등록 정보 수정, 목록 조회와 삭제
- 등록 당시 영양성분 스냅샷
- 기존 재고와 재구매 수량 병합
- 소진 예정일·상태·재구매 알림 계산
- 유통기한 입력과 만료 처리
- AWS·AI 연결

## 시나리오

### 기본 흐름

1. 로그인 사용자가 DB 카탈로그 제품과 복용 계획을 제출한다.
2. 서비스가 날짜·수량 규칙을 검증하고 저장소가 카탈로그 제품 존재를 확인한다.
3. 새 care_items 행을 현재 사용자 소유로 저장한다.
4. API가 생성된 항목을 201로 반환한다.

### 실패와 경계

- 인증 쿠키가 없거나 유효하지 않으면 401 `AUTH_REQUIRED`다.
- 제품이 없으면 404 `PRODUCT_NOT_FOUND`다.
- UUID·필드 범위·날짜 순서·수량 관계가 잘못되면 422 `VALIDATION_FAILED`다.
- DB 장애는 세부정보 없는 503 `SERVICE_UNAVAILABLE`다.
- 생성 API이므로 멱등하지 않으며 같은 요청은 별도 항목을 생성한다.
