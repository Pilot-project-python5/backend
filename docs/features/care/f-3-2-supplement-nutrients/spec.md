# F-3.2 영양제 성분 연결

## 목표

영양제 복용 항목을 등록할 때 제품의 현재 활성 구성 성분과 단위당 함량을 별도
스냅샷으로 보존한다. 이후 제품·성분 카탈로그가 바뀌어도 이미 등록된 복용 항목의
예정 섭취량 계산 입력이 달라지지 않게 한다.

## 사용자 이야기

사용자로서, 제품 정보가 나중에 변경되더라도 내가 등록했을 당시의 영양성분 기준으로
일관된 예정 섭취량을 확인하고 싶다.

## 비즈니스 규칙

1. 기존 `POST /api/v1/care/items`에서 SUPPLEMENT 제품을 등록할 때만 성분
   스냅샷을 생성한다.
2. 스냅샷 대상은 등록 트랜잭션에서 조회한 `is_active=true` 영양성분 연결이다.
3. 각 스냅샷은 nutrient_id, 당시 nutrient_name, amount_per_unit과 unit을 보존한다.
4. 같은 복용 항목과 영양성분 조합은 한 번만 저장한다.
5. MEDICATION 제품은 복용 항목만 생성하고 성분 스냅샷은 만들지 않는다.
6. 활성 성분이 없는 영양제도 등록은 성공하며 스냅샷은 0건이다.
7. 복용 항목과 모든 스냅샷은 하나의 DB 트랜잭션으로 저장한다. 하나라도 실패하면
   복용 항목을 포함해 전체를 롤백한다.
8. 등록 후 제품 성분 함량·단위·연결 또는 영양성분 이름·활성 여부가 바뀌어도 기존
   스냅샷 값을 갱신하거나 삭제하지 않는다.
9. F-3.1에서 이미 생성된 영양제 복용 항목은 0012 적용 시점의 활성 카탈로그를
   기준으로 한 번 백필하고 이후에는 변경하지 않는다.
10. 기존 등록 API의 요청·201 응답·오류·인증 계약은 그대로 유지한다.

## 포함 범위

- 영양제 등록 시 활성 성분 스냅샷 생성
- 복용 항목과 스냅샷의 원자적 저장·롤백
- 의약품·성분 없음 경계 처리
- care_nutrient_snapshots ORM·0012 마이그레이션·ERD
- 기존 영양제 복용 항목의 업그레이드 시점 백필
- 단위·통합·계약·인수 테스트와 API 문서

## 제외 범위

- 성분별 일일 예정 섭취량 계산과 단위 변환·합산
- 영양소 기준 CSV와 달성 비율
- 스냅샷 조회·수정·삭제 API
- 의약품의 영양소 합계 포함
- 제품·성분 카탈로그 쓰기 API
- AWS·AI 연결

## 시나리오

### 기본 흐름

1. 로그인 사용자가 활성 성분이 연결된 영양제 제품을 등록한다.
2. 저장소가 제품 유형과 활성 성분을 한 트랜잭션에서 조회한다.
3. 새 care_items 행과 성분별 care_nutrient_snapshots 행을 함께 저장한다.
4. API는 F-3.1과 같은 201 응답을 반환한다.

### 실패와 경계

- 인증·요청 검증·제품 없음·DB 장애 응답은 F-3.1 계약을 유지한다.
- MEDICATION 등록은 성공하지만 스냅샷이 0건이다.
- 활성 성분이 없는 SUPPLEMENT 등록도 성공하고 스냅샷이 0건이다.
- 스냅샷 저장 실패는 503이며 care_items와 일부 스냅샷이 남지 않는다.
- 동일 제품의 재등록은 서로 다른 care_item_id 아래 독립 스냅샷을 만든다.
- 같은 care_item_id와 nutrient_id의 중복은 DB 고유 제약으로 거부한다.

## 미결 질문

- 없음. 기존 F-3.1 영양제 행은 정확한 등록 당시 값이 없으므로 0012 적용 시점의
  활성 카탈로그로 최선 백필한다. 승인 시점 공유 로컬 개발 DB의 care_items는 0건이다.
