# F-3.10 의약품 관리

## 목표

로그인 사용자가 서비스 DB가 관리하는 의약품만 조회해 복용 항목으로 선택하고, 효능·
복용법·주의·보관과 정보 출처를 확인할 수 있게 한다. 영양제와 의약품을 같은 Product·
CareItem 흐름으로 관리하되 의약품을 영양소 계산에 포함하지 않는 기존 경계를 유지한다.

## 사용자 이야기

사용자로서, 직접 작성한 불완전한 이름 대신 서비스가 관리하는 의약품과 복약 정보를
확인해 내 복용 목록에 정확한 제품을 등록하고 싶다.

## 비즈니스 규칙

1. 사용자는 의약품을 생성·수정하거나 카탈로그 밖 제품을 직접 입력할 수 없다.
2. 의약품 카탈로그는 `Product.product_type=MEDICATION`, `is_published=true`이며
   MedicationDetail이 존재하는 DB 시드 제품만 제공한다.
3. 의약품 분류는 1차에 일반의약품 `OTC`와 전문의약품 `PRESCRIPTION` 두 값만 쓴다.
4. 상세의 필수 정보는 품목 추적 코드, 유효성분 요약, 효능, 용법·용량, 주의사항,
   보관법, 출처명·HTTPS URL과 출처 검토일이다.
5. 목록은 Product의 `sort_order`, `sku` 순으로 결정적으로 페이지 처리하고 상세가
   없거나 비게시·영양제인 ID는 노출하지 않는다.
6. 목록과 상세는 로그인 회원만 사용할 수 있고 사용자 ID를 요청으로 받지 않는다.
7. 로컬 1차 시드는 UI·API 검증용 예시 의약품임을 데이터에 명시한다. 실제 운영
   전환 시에는 품목별 공식 출처를 검토한 데이터로 교체해야 한다.
8. 의약품은 기존 F-3.1 등록·F-3.4 목록·F-3.7 소진 흐름을 그대로 사용하지만
   F-3.5·F-3.6 영양소 계산에서는 계속 제외한다.

## 포함 범위

- 보호된 의약품 목록·상세 API와 Swagger 계약
- Product와 1:1인 MedicationDetail 모델·마이그레이션·ERD
- 결정적·멱등 로컬 의약품 제품·상세 시드와 실제 존재하는 로컬 이미지
- 인증·필터·페이지·404·DB 장애 계약 테스트
- 영양소 계산 제외 회귀 검증

## 제외 범위

- 사용자 직접 입력, 운영자 CRUD와 처방전 업로드
- 의약품·영양제 상호작용, 금기 판정과 개인화된 복약 지시
- 식약처 자동 수집·동기화와 운영 데이터 승인 워크플로
- 약국 재고·구매·결제, 처방 조제와 실제 복용 기록
- 유통기한 입력·상태·알림(F-3.11 이후)

## 시나리오

### 기본 흐름

- 로그인 사용자가 의약품 목록을 열면 게시된 의약품 상세 보유 제품만 안정 순서로
  조회하고, 하나를 선택하면 출처를 포함한 전체 복약 정보가 반환된다.
- 사용자는 반환된 product_id를 기존 복용 항목 등록 API에 보내 독립 CareItem으로
  등록하며 해당 항목은 일일 영양소 합계에서 제외된다.

### 실패와 경계

- 인증 없음은 401, 영양제·미게시·상세 없음·없는 UUID 상세는 모두 404
  `MEDICATION_NOT_FOUND`, 저장소 장애는 503이다.
- 빈 페이지는 200과 빈 items를 반환하고 page_size는 1~100으로 제한한다.
- 시드를 두 번 실행해도 같은 제품·상세 행으로 수렴하며 다른 제품은 삭제하지 않는다.
- MedicationDetail은 Product 삭제 시 CASCADE되고 Supplement 연결은 시드와 저장소
  검증에서 거부한다.

## 미결 질문

- 없음. 사용자가 모호한 사항을 자율 추론해 근거를 문서화하도록 승인했다. 1차 필수
  필드와 OTC/PRESCRIPTION 분류는 사용자 선택·표시·출처 추적에 필요한 최소 계약으로
  확정하며 로컬 시드가 실제 의료 지시가 아니라는 경계를 명시한다.
