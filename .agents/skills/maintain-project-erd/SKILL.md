# 프로젝트 ERD 유지

데이터 변경을 승인된 기능 계약과 저장소 ERD에 함께 반영한다.

## 작업 절차

1. AGENTS.md, docs/product/requirements.md, docs/product/scope.md, docs/architecture/erd.md와 대상 Feature Packet을 읽는다.
2. 변경되는 엔티티, 필드, 관계, 카디널리티, 제약, 인덱스, 상태 이력과 개인정보를 식별한다.
3. 대상 design.md의 데이터 설계와 ERD 영향에 변경 전·후 구조를 기록한다.
4. 데이터 소유권, 삭제, 재구매, 계산 또는 호환성 정책이 모호하면 구현 전에 사용자에게 질문한다.
5. 승인된 설계만 docs/architecture/erd.md의 Mermaid와 설명에 반영한다.
6. 신규·변경 마이그레이션의 적용 순서, 백필, 기존 데이터 영향과 롤백 위험을 기록한다.
7. scripts/validate_erd.py를 실행한다.
8. 구현이 존재하면 ORM 모델, 마이그레이션, DB 제약과 ERD를 비교한다.

## 모델링 규칙

- 저장소 문서만 사용하고 외부 ERD나 요구사항 페이지 연결을 전제로 하지 않는다.
- Mermaid 엔티티명은 대문자 snake_case, 실제 테이블은 소문자 snake_case로 대응한다.
- 모든 엔티티에 PK를 명시하고 관계 양쪽의 카디널리티를 표시한다.
- FK, UNIQUE, CHECK, 인덱스와 삭제·이력 정책을 Feature Packet에 명시한다.
- 파생값은 저장 여부와 재계산 시점을 설명한다.
- 민감정보는 최소화하고 암호화·해시·로그 제외 방식을 기록한다.
- 이미 적용된 마이그레이션을 조용히 다시 쓰지 않는다.
- 카탈로그 변경으로 기존 성분 스냅샷을 덮어쓰지 않는다.
- 의약품을 영양소 합계에 포함하지 않는다.
- 데이터 변경이 없으면 ERD를 억지로 수정하지 말고 변경 없음과 이유를 기록한다.

## 검증 명령

~~~bash
python .agents/skills/maintain-project-erd/scripts/validate_erd.py
~~~

구현 이후에는 기능별 마이그레이션 검사와 저장소 전체 검증도 실행한다.

## 결과물

영향 엔티티, 관계·제약 변경, 갱신한 파일, 마이그레이션 고려 사항, 검증 결과와 미결 질문을 반환한다. 사용자 요청 없이 마이그레이션이나 운영 코드를 구현하지 않는다.
