# SDD 기능 검증

기능 하나가 승인된 계약과 일치한다는 근거를 만든다.

## 작업 절차

1. AGENTS.md, docs/product/requirements.md와 대상 Feature Packet을 읽는다.
2. 변경 사항이 주 기능 ID 하나와 선언된 의존성만 다루는지 확인한다.
3. 모든 인수 조건 ID를 자동 테스트 하나 이상 또는 명시적으로 정당화한 수동 검사와 연결한다.
4. 가장 좁은 기능 검사부터 실행한 뒤 저장소 전체 검증 명령을 실행한다.
5. 데이터 변경이 있으면 docs/architecture/erd.md, ORM 모델, DB 제약과 마이그레이션을 비교하고 ERD 검증기를 실행한다.
6. 마이그레이션이 바뀌었다면 빈 로컬 PostgreSQL DB와 지원하는 이전 스키마에서 검증한다.
7. 생성된 OpenAPI를 기능 설계와 비교하고 예시, 오류, 인증과 상태 코드를 확인한다.
8. D-day, 유통기한과 알림 테스트에는 가짜 시계와 가짜 이메일 발신기를 사용한다.
9. 테스트와 시드 데이터가 결정적이며 실제 개인정보나 건강정보를 포함하지 않는지 확인한다.
10. 최종 변경 사항에서 관련 없는 수정, 비밀정보, 임시 산출물과 문서화되지 않은 동작을 확인한다.

## 필수 근거

- 기능 ID와 Feature Packet 경로
- 인수 조건 충족 범위
- 실행한 명령과 종료 결과
- 해당하는 경우 마이그레이션과 시드 결과
- 데이터 변경 시 ERD 검증과 실제 스키마 비교 결과
- 해당하는 경우 OpenAPI 계약 결과
- 남은 위험 또는 검증하지 못한 동작

## 실패 규칙

- Feature Packet이 없거나 승인되지 않았거나 최신 상태가 아니거나 차단 중인 미결 질문이 있으면 실패로 처리한다.
- 근거가 없는 인수 조건이 하나라도 있으면 실패로 처리한다.
- 1차 기능 실행에 외부 AWS 또는 AI 의존성이 필요하면 실패로 처리한다.
- Swagger와 구현된 요청·응답 동작이 다르면 실패로 처리한다.
- 데이터 모델이 Feature Packet 또는 로컬 ERD와 다르면 실패로 처리한다.
- 검사를 통과시키기 위해 테스트를 약화하거나 삭제하지 않는다.

## 결과물

PASS 또는 FAIL로 시작한다. 이어서 기능 이력에 재사용할 구현 요약·검증 근거, 차이와 가장 작은 다음 조치를 보고한다. 사용자가 코드 수정을 요청하지 않았다면 직접 구현하지 않는다.
